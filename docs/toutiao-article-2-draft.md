# 用 AI 生图做游戏第二期：主菜单按钮三态 + 主角行走 Sprite，试了一百多张图才勉强能用

接上期用 GPT-Image-2 生成了游戏主菜单背景和标题，这期讲两个更难啃的骨头：**主菜单按钮的三态效果**和**主角的四方向行走动画 Sprite**。前者浪费了四个版本才搞明白，后者更是烧了 ¥8+ 和上百次尝试。

---

## 一、主菜单按钮：你以为拼图层很简单？

### 失败的 v1~v4：拆分部件再拼图

一开始的想法很自然：把按钮拆成"底框"和"文字"两层，分别让 AI 画，然后用 PIL 拼到一起。这样文字可以单独调整，按钮的 normal/hover/pressed 三态也能分别生成。

但实际效果惨不忍睹：

- **色调不统一**：底框是暗金属色，文字是金色，但两个图层的光源方向、色温完全不同，拼起来一眼假
- **边缘对不上**：底框的内阴影和文字层的定位总是差几个像素，强迫症直接去世
- **hover 状态格格不入**：hover 状态的发光底框和 normal 的文字拼在一起，明暗关系不合理——正常是整体发光，不是只有框发光文字不变

四个版本，全部报废。

### v5：全图一次性生成

改成**整张图一次性出**——按钮的暗金属边框、宝石角饰、金文字、hover 的发光效果，全部写在一个 prompt 里：

```
Button style: Dark ornate metal frame with emerald green gradient fill, 
gem corner decorations, gold Chinese text centered. 
1536×1024 landscape, wuxia RPG menu screen.
```

结果：**一次成功**。单个按钮包含三种状态一气呵成，光影统一。

**教训**：AI 单次生成能把全局光影/色调/构图保持一致，分件拼图反而破坏了这种全局性。

> 下图是最终的主菜单完整画面（背景+标题+人物+三个按钮），从这张 1536×1024 的图里我们手动裁出按钮区域，再在 Godot 里精调位置。

现在的问题是按钮的 hover 效果还不够明显，后续需要单独优化。

## 二、主角 Sprite：最崩溃的部分

游戏需要主角冷孤云在地图上四个方向（上下左右）走路。一个方向一个行走循环至少 4~8 帧，加上 idle 站立动作，总共需要 **几十帧连续一致的角色图像**。

GPT-Image-2 是个电影级生图模型，不是 sprite 引擎。以下是我们踩过的坑：

### 方案一：逐帧分画（完全失败）

思路：一帧一帧地让 AI 画，每帧 prompt 写明"冷孤云走路第 N 帧，左脚在前"之类的。

结果：

> 图1：冷孤云走路 f01——蓝色外袍、皮肤偏白  
> 图2：冷孤云走路 f02——外袍突然变成浅蓝、皮肤偏黄  
> 图3：冷孤云走路 f03——整件袍子颜色提亮了至少 20%  
> 图4：冷孤云走路 f04——脚钉在原地没动，像在漂移不是走路  

**每帧的衣服颜色、肤色、身材比例、光影方向都不同**。AI 没有"视觉记忆"，每张图都重新随机了一次角色外观。拼成一个 GIF 循环时，人物在疯狂闪变。

### 方案二：关键帧锚定 + 参考图 edits（部分改善）

改策略：先跑 f01 纯文生成，满意后锁定为"锚帧"。f02~f04 走 image edit 模式——以 f01 为参考图传给 API，prompt 只描述"把左腿改成右腿在前"等动作差异。

效果好了不少——颜色基本对上了，身体比例也一致了。但新问题：

- **脚步相位模糊**：模型对"抬多高""哪只脚承重"的理解很粗糙，经常两脚同时离地或同时着地，不像走路
- **下半身僵化**：edits 为了保脸和上半身，倾向于不动下半身，导致四帧看起来"只有袍摆微动"
- **四帧不够**：4 帧走路太跳跃，需要 8 帧循环才能顺滑

### 方案三：一次性生成完整 Sprite Sheet（接近可用）

最终放弃逐帧策略，改用**一次生成一整张 sprite 表**：4 个方向 × 4 帧 = 16 格全部在一张图里，prompt 写明网格排布和脚部相位。

这个方案终于输出了能看的东西——至少同一张图内各帧的角色外观是一致的。

但问题依然很多：

> 图5：4向4帧行走表（第一次成功版）——人物比例对，但每一帧的脚线根本不在同一水平面上，GIF 一播人物在上下弹跳

后来加了"强制同一脚底基线""固定格内身体中心"等约束，但模型的理解准确率只有大概 1/5。

**试了上百次，只有一两次算"接近可用"的。**

### 方案四：8 帧闭环优化（仍然不稳定）

4 帧改成 8 帧，单行生成向右走。额外要求第 9 格等于第 1 格（loop check），迫使第 8 帧自然过渡到第 1 帧。

| 方向 | 结果 |
|------|------|
| 右走 8 帧 | 可用，基线偏差 4px |
| 左走 | 右走镜像（零 API 成本） |
| 下走 8 帧 | 脚步相位不自然，像"原地轻微踏步" |
| 上走 8 帧 | 同上，观感失败 |

上下方向的 8 帧无论如何都解决不了"两只脚协调交替"的问题——多次尝试后模型只会把中间帧画得很相似，导致播放时像在抖动而不是走路。

**最终妥协方案**：左右走用 8 帧，上下走退回到 4 帧慢速版。四个方向帧数不一致，但至少观感是通的。

## 三、抠图透明底：又一个坑

GPT-Image-2 不支持透明背景，所有 sprite 生成出来都是白底或场景底。每张图都要用 rembg 抠图。

抠图本身不复杂，但**抠完的毛边**需要人工修补——尤其是深色袍摆和深色背景交界的地方，rembg 经常把袍子边缘也抠掉了。

spritesheet 抠完后还要逐格裁切，用 `build_sprite_preview.py` 按统一锚点（底部居中）导出固定画布的帧。如果不用统一锚点直接串 GIF，人物就会跳来跳去。

## 四、成本总结

| 项目 | 尝试次数（估算） | 成功数 | 花费 |
|------|:--:|:--:|------|
| 主菜单按钮（v1~v4 拼图） | ~15 次 | 0 | ¥8+ |
| 主菜单按钮（v5 全图） | ~3 次 | 1 | ¥3.6 |
| 主角行走逐帧（方案一） | ~12 次 | 0 | ¥4+ |
| 主角行走 edits（方案二） | ~20 次 | 部分 | ¥3+ |
| 主角行走 sheet（方案三） | ~30 次 | 2~3 | ¥6+ |
| 主角行走 8 帧闭环（方案四） | ~25 次 | 3~4 | ¥5+ |

总共大概 **¥30+** 和上百次 API 调用，才凑出一套勉强能用的主角四方向 sprite。

## 五、结论

1. **拼图层不如一次出全图**——主菜单证明了这一点。AI 的全局一致性是它最大的优势，不要试图自己拼。

2. **多帧动画是 AI 生图最大的短板**——GPT-Image-2 没有帧间记忆，即使传参考图也有概率漂移。逐帧一致性至今**没有稳定方案**。

3. **方向差异明显**——侧向（左右）走得顺，正面/背面（上下）几乎不可控。这可能跟训练数据中"侧向行走"的样本更多有关。

4. **成本远高于预期**——如果你也想用 AI 做 sprite，建议先准备好 ¥50~100 的试错预算，并且对"最终可能还是要手动修"有心理准备。

5. **抠图是小事，锚点对齐才是关键**——rembg 一键搞定透明底，但 sprite 播放不跳帧需要统一的画布和锚点规范。

下一步：这套 sprite 接入 Godot 后看看实际游戏中的效果，以及继续优化上下两个方向。也许需要换一种思路，比如用视频生成模型（Seedance）来做动画，再转成 sprite 帧。
