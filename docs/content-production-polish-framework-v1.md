# 游戏内容生产与润色框架 v1

> 状态：第一章试行版  
> 适用：地图场景、战斗内容、角色精灵、剧情与任务  
> 参考：Claude Code Game Studios 的 `team-level`、`team-combat`、`team-narrative`、`art-bible`、`asset-spec` 与 `content-audit` 工作流。本文只吸收内容生产方法，不引入其 49 Agent 组织结构或逐文件审批流程。

## 1. 目标

把内容制作从“发现问题后局部修补”改为同一条可验收生产链：

```text
内容目的
  → 玩家行为与体验节奏
  → 空间 / 战斗 / 叙事 / 美术规格
  → 数据和资源制作
  → Godot 接入
  → 自动化合同
  → 1080P 实机目检
  → 内容目录同步
```

任何内容只有同时满足“数据存在、运行时可达、画面合格、玩家能理解、测试能拦回归”，才算完成。

## 2. 四条内容生产线

### 2.1 地图场景

固定顺序：

1. 定义本场景的剧情目的、玩家情绪和预计停留时间。
2. 先画结构图，标出主路线、可选路线、地标、建筑岛、出入口、NPC、任务物件和遮挡区。
3. 审核相邻场景的双向连接与出生点，不允许先做孤立场景。
4. 用结构图作为生图硬参考；画风参考只控制美术，不得覆盖道路结构。
5. 从同一结构生成 `walkable_areas`、`blockers`、`portals`、`interactions`、`actor_fade_zones`。
6. 自动验证关键路径、支路、房门、NPC接近点和出口；再做1080P滚动、层级、清晰度和性能目检。

场景交付物：

- 一张布局参考图。
- 一份场景意图说明。
- 一张正式无人物底图。
- 同源导航数据。
- 关键探针测试。
- 一张全图标注图和至少一张实机截图。

禁止：

- 先生成复杂成品图，再凭肉眼猜碰撞。
- 画面有路但导航不通。
- 出口放在草丛、墙体或建筑屋顶。
- 通过放大低分辨率图片制造大地图。
- 为烘焙在背景里的建筑重复叠加一栋前景建筑。

### 2.2 战斗内容

每场战斗先回答四个问题：

1. 这场战斗教会或检验玩家什么？
2. 敌人的战术身份是什么？
3. 玩家胜利后获得什么新信息、资源或路线？
4. 失败或准备不足时，玩家有什么可理解的改进方向？

制作顺序：

```text
战斗目的
  → 敌人组成与推荐强度
  → 行动模式和技能公式
  → 角色动作 / VFX / 音效语义
  → 奖励与剧情后果
  → 单挑、队伍、状态、击杀结算回归
```

验收必须覆盖：

- 普通、精英、Boss 的轮廓和招式可一眼区分。
- 敌人的单体、群体、增益、控制行为与身份一致。
- 角色动作先于伤害与特效结算，蒙版和全屏演出不会吞掉攻击动作。
- 敌人死亡后立即检查胜负，不留下空操作回合。
- 战斗奖励服务当前成长阶段，不提前投放后期神兵绝学。
- 数值测试与视觉目检分开；自动测试不能代替动作、打击感和特效语义验收。

### 2.3 角色立绘与精灵图

每名重点角色必须先有身份锚点：

- 年龄、体型、脸型、发型。
- 服装主色、材质和身份配件。
- 武器、惯用手、携带方式。
- 玩家、伙伴、普通NPC、敌人的轮廓区分规则。

Field 与 Battle 是两套表现合同：

- Field：旅行状态、四向、完整脚部、稳定尺度、自然步态；武器可以入鞘、背负或收纳。
- Battle：备战、移动、攻击、受击、倒地；武器必须进入战斗状态并保持同一只手、同一尺寸和连续动作。

发布门禁：

1. raw 母图逐格检查头、脚、衣摆、武器安全带。
2. processed/runtime 保留可追溯参数和来源。
3. 逐帧 alpha、尺寸、脚底余量和锚点自动检查。
4. 固定脚底 GIF 检查滑步、换手、跳位和比例漂移。
5. 四向接触表检查身份和服装一致性。
6. 游戏内与背景、NPC、敌人同屏检查尺度和层级。

### 2.4 剧情与任务

每章先确定：

- 一个章标题与核心疑问。
- 玩家在本章亲手完成的行动。
- 至少一条可验证的新证据或人物关系变化。
- 主线关键路径、自由调查顺序和支线回流点。
- 章末冲突如何把玩家送往下一章。

任务制作顺序：

```text
任务缘由
  → 玩家确认接取
  → 地点目标
  → 独立行动或调查
  → NPC进行中复访
  → 交付 / 验证
  → 奖励与后续影响
```

验收规则：

- 任务资源存在不等于任务已接入；必须能反查接取、推进和完成节点。
- 普通采集、战斗、寻人任务不得在同一次交互中接取并完成。
- HUD 只显示地点目标，任务日志才显示完整背景，避免剧透。
- NPC首次、拒绝后、进行中、可交付、完成后的对白必须区分。
- 主线必要旗标不能由可拒绝支线提供。
- 同一人物、证据与章节归属必须和现行故事目录一致；兼容旧档资源不能冒充现行内容。

## 3. 跨内容发布门禁

每个内容批次必须同时回答：

| 维度 | 必须提供的证据 |
|---|---|
| 设计 | 玩家目标、情绪、节奏、依赖和验收条件 |
| 空间 | 主路、支路、地标、入口、出口、阻挡、任务物件 |
| 叙事 | 接取、进行中、完成、后果和下一步 |
| 战斗 | 目的、阵容、技能、奖励和强度位置 |
| 美术 | 身份锚点、规格、预览、运行资源和来源 |
| 运行 | Godot严格解析、专项测试、完整流程测试 |
| 视觉 | 1080P截图或GIF人工确认 |
| 目录 | 江湖全录、任务卷宗和进展快照同步 |

### 批次 E：历史支线整理（已完成）

- 接入悬崖采药的委托、任务物件、采集、回交与复访闭环。

验收：接取后才显示任务物件，采集不提前结算，回交只发奖一次；网页明确显示三项内容决策。

## 6. 执行原则

- 先完成批次 A，再继续做新地图或新角色，避免在旧正典上继续扩内容。
- 每批只改一个共享数据主干，地图、剧情、战斗和美术写改保持串行。
- 自动化通过只证明合同成立；地图观感、动作自然度、身份一致性和剧情节奏仍由人工实机验收。
- 新内容完成后必须同步 `current-progress.md`、角色记忆、`experience-log.md` 和江湖全录。
